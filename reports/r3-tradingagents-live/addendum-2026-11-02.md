# R3 pre-registration addendum — 2026-11-02

Written when the integrity release of the ledger (v2, milestone M1) was
prepared, before the code reaches `main`. It records two places where the
running ledger will differ from what [`preregistration.md`](preregistration.md)
§9 and [`addendum-2026-10-29.md`](addendum-2026-10-29.md) §4 describe. The
models, tasks, window, rating mapping, prompts and verdict rules do not change.
The files above are not edited.

## 1. Verification of entries: push time, not run start

**Registered (§9).** An entry counts only if its Actions run is a run of the
ledger workflow on `main` that *started* before the fill session's open.

**From the first schema 2 entry.** Entries written by the new recorder
(`schema: 2`) count only if all of these hold:

- the jobs of the entry's own run attempt show that the step
  `Commit and push ledger entries` of `ledger.yml` succeeded before the open;
- the commit that added the entry file was authored by `github-actions[bot]`
  with the workflow's message, added exactly the entry's bytes, and descends
  from the run's head commit;
- the entry's `decision_sha256` matches its content.

This is stricter than the registered rule: a run that started before the open
but pushed after it no longer counts.

**Earlier entries.** The entries committed before this change (nine at the
time of writing) are `schema: 1` and keep the registered run-start verification. The ledger record
lists the rule that verified each entry (`fit.verified_by`: `run-start` or
`push-time`), so the final report must state that the evidence is mixed and
how many entries each rule covered.

**What the proof does not show.** Git authorship is not a signature: someone
with push rights could forge a workflow commit. The commit SHA that the push
step writes to its step summary cannot be read through the API and is not
checked.

## 2. Cost cap: a decision that does not fit is not recorded

**Registered (addendum 2026-10-29 §4).** When the month's cost reaches the cap,
the ledger writes a hold with reason `budget cap`, which counts as a missed
session.

**From the first schema 2 entry.** Before a decision the ledger reserves the
entrant's worst-case cost for one decision (`max_cost_per_decision_usd`, $0.70
for TradingAgents, rounded up from the largest dry-run decision, $0.694). If
the month's cost so far plus the reservation would exceed
`LEDGER_MONTHLY_BUDGET_USD` (60), no model is called, **nothing is written**,
and the job fails for that entrant. The session is then a session without an
entry, which scores as a hold and is counted in `missed_sessions`, as before;
what changes is that no `budget cap` hold entry exists. A decision that reports
no token usage is billed the reservation, not zero.

The cap values themselves ($60 a month, $200 for the window) do not change.
